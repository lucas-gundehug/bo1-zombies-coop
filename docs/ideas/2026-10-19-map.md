# Brief: an in-game map for the cheat-menu fork

Starting point for a new session. Read `AGENTS.md` first (how the fork works, how to test in the real game). This is
a brief, not an approved design: brainstorm the open questions with Lucas before building.

## What Lucas wants (his words, 2026-10-19)

"I get lost in the game about where my friends are, what room I'm in, what doors I have not unlocked yet and would
like a map for that." No teleport.

- Where his friends are, in their player colours (the co-op card's `PLAYER_COLORS`, src/ui/card.js).
- Which room he is in, with readable room names.
- Which doors and debris are still closed, with their price.
- Shape: first a **big map that pops up on a key**; later maybe a **small map in a corner** that moves with him.

## What we already have to build on

The cheat menu (v2.2.2.1, merged to `main`) proved the pipeline end to end on all ten maps, Hell mode and co-op
(also with both players on this fork):

- A game script loaded as a vel.gg mod (`src/cheats/gsc/_cheats.gsc`, written to OPFS and named in `fs_mods` by
  `src/cheats/setup.js`). It runs only on the host's server and sees every player.
- The script publishes data in dvars; `src/cheats/bridge.js` reads them by sending the dvar name as a console command
  and catching the engine's `"name" is: "value^7"` print. One dvar value should stay under ~400 characters (a ~1 KB
  log line was dropped in the spike), so long data is split into numbered chunks (see `cheats_weapons_<i>`).
- A key that shows UI without pausing: `src/cheats/hotkey.js` (M). It hides the one pointer unlock it causes from
  vel.gg, which would otherwise press Escape and pause everyone.
- Tests in the real game: `test/cheats-e2e.mjs` (scenarios, screenshots with `SHOTS=`), co-op with
  `test/e2e.mjs` + `CHEATS=1` / `GUEST_EXT=`.

The map should reuse these: extend the same script and bridge (or a sibling `src/map/` with its own dvars), not a
second mod.

## Data the game can give (to verify early, in game)

| Need | Where it likely is (BO1 GSC) | Verified? |
| --- | --- | --- |
| Player positions, view direction, floor | `player.origin`, `player GetPlayerAngles()` | origin yes (used for power-ups) |
| Map rooms ("zones") | `level.zones[name]` with `.volumes` (info_volume entities) and `.is_enabled` (opened) | no |
| Room each player is in | `player IsTouching( volume )` over each zone's volumes, or the zone manager's own helper | no |
| Closed doors / debris and price | `GetEntArray( "zombie_door", "targetname" )`, `"zombie_debris"`; cost in `zombie_cost`; opened ones are deleted or flagged | no (the decompiled repo's sandbox mod opens them via these triggers) |
| Points of interest (optional) | perk machines (`zombie_vending`, already used), Mystery Box (`level.chests`), Pack-a-Punch (`zombie_vending_upgrade`), power switch (`use_elec_switch`) | partly |
| A floor plan to draw | path nodes (`GetAllNodes()` if this build has it) grouped by zone, drawn as room shapes | no |

The game has **no overview image**. The plan is to draw a schematic floor plan from data, not a picture.

## Suggested architecture (the next session decides)

- **Static per map, dynamic per moment.** The floor plan (room shapes from path nodes, room names, door positions)
  never changes for a map: generate it once per map with a Playwright script (like `test/cheats-e2e.mjs`, one run per
  map), save it as JSON in the repo (e.g. `src/map/plans/<map>.json`) and bundle it. Live data stays small: player
  positions and rooms, which doors are open, refreshed about once a second through the bridge.
- **Room names** are technical in the game (e.g. `foyer_zone`): a hand-written name table per map, like
  `src/cheats/names.js`, with a readable fallback.
- **Drawing**: an overlay over the game (not inside the 312 px card), e.g. a canvas or SVG in the extension's shadow
  root, scaled to the map's bounds. Players as coloured dots with an arrow for the view direction, closed doors as a
  lock with the price, the current room highlighted.
- **Floors**: Five and Kino have several levels. Split rooms by height and show the floor the player is on, with a
  way to look at the others.

## Open questions for Lucas (brainstorm before building)

1. Which key opens the big map, and should it be "hold" or "press to toggle"? (Tab is the game's scoreboard; M is the
   cheat menu.)
2. Should the big map pause nothing and let him keep moving, like the cheat menu does?
3. Anything else on the map: perk machines, Mystery Box, Pack-a-Punch, the power switch?
4. The small corner map: now or later, and does it rotate with him or stay north-up?
5. Friends' names next to their dots, or only colours?

## Risks to check first (a short spike, as for the cheat menu)

- That zones, doors and path nodes are reachable from the script on a few maps (Kino, Five, Moon).
- How big the node data is per map, and how long reading it through the console takes (it is a one-off per map if
  the plans are generated offline).
- Whether a full-screen overlay keeps the game running smoothly on Lucas's gaming laptop.
